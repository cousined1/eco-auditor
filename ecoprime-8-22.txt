## Fix policy

### Severity levels

- P0 — security exposure, auth bypass, tenant escape, secret leakage, data loss, broken production-critical flow
- P1 — major billing/auth/data integrity defects, broken builds, failing core tests, severe UX blockers
- P2 — accessibility, SEO, performance, reliability, maintainability issues with meaningful user or ops impact
- P3 — minor polish, low-risk cleanup, non-critical quality improvements

### Change strategy
For auth, billing, webhooks, DB schema, secrets, infra, retention, or destructive operations:
- prefer the smallest safe fix,
- add or update tests,
- isolate the change in its own commit,
- mark clearly if human review is required.

General rules:
- no new dependency unless necessary and justified,
- prefer patch/minor upgrades,
- no hardcoded secrets,
- update `.env.example` for any required variable changes,
- keep commits small, scoped, and reviewable,
- preserve existing architecture unless a defect requires change.

## Verification standard

Do not report an issue as confirmed unless supported by at least one of:

- code evidence,
- runtime evidence,
- test failure,
- reproduction steps,
- config evidence,
- dependency audit output,
- build/lint/typecheck result.

For every confirmed issue, include:
- why it is a real issue,
- how it was verified,
- what was changed,
- how the fix was re-verified,
- remaining risk or follow-up need.

If you suspect an issue but cannot verify it, label it:
`Unconfirmed — needs review`

Do not present unverified suspicions as facts.
